# B13 — Audit tecnico: refresh token e gestione sessioni

## Modello attuale (fotografia)

Doppio cookie HttpOnly + store server-side dei soli **refresh** per `jti`:

| Pezzo | Dove | Comportamento |
|---|---|---|
| Access JWT | `jwt_tokens.create_access_token` | HS256, `type=access`, `sub`/`email`/`role`, TTL default **15 min** (`ACCESS_TOKEN_MINUTES`) — **senza `jti`** |
| Refresh JWT | `create_refresh_token` | HS256, `type=refresh`, `sub` + **`jti` uuid**, TTL default **7 giorni** |
| Cookie | `auth._set_auth_cookies` | `access_token` + `refresh_token`, HttpOnly, `Secure`/`SameSite` da `COOKIE_SECURE` |
| Store | `session_store.store_refresh` | `refresh_tokens`: `{jti, user_id, expires_at, created_at}` |
| Validità | `is_refresh_valid` | refresh accettato **solo se** `jti` ancora in Mongo |
| Rinnovo | `POST /auth/refresh` | verifica refresh → emette **solo nuovo access**; **non** ruota il refresh |
| Logout | `POST /auth/logout` | `revoke_refresh` (`delete_one` jti) + clear cookie |
| FE | `api.js` `refreshSession` | su 401: un solo refresh in volo, poi retry; bootstrap in `auth.jsx` |

CSRF: con `COOKIE_SECURE=true` è attivo; `/api/auth/refresh` è **esente** (prova = cookie refresh HttpOnly).

---

## 1. Rinnovo delle sessioni

### GIÀ PRESENTE
- Access corto + refresh lungo, documentato nel codice.
- `POST /auth/refresh`: cookie refresh → decode → `type==refresh` → `is_refresh_valid` → user attivo → nuovo `access_token` cookie → `_public(user)`.
- FE: silent refresh su fallimento `/auth/me` e su 401 API (`refreshSession` single-flight).
- Refresh controlla `is_active` (login/refresh sì; `get_current_user` no — già B1).

### PARZIALMENTE PRESENTE
- Il rinnovo **prolunga solo l’access**. Il refresh resta lo stesso fino a scadenza 7g o logout: non c’è sliding window sul refresh.
- Ruolo/email nell’access nuovo vengono dal **DB** al refresh (buono); l’access vecchio resta valido fino a `exp` anche se il ruolo è cambiato.

### ASSENTE
- Rotazione del refresh a ogni `/auth/refresh`.
- Endpoint “estendi sessione” esplicito oltre al refresh automatico.
- Revoca access in anticipo (no denylist access / no `jti` sull’access).

### DA VERIFICARE
- Valori effettivi di `ACCESS_TOKEN_MINUTES` / `REFRESH_TOKEN_DAYS` in produzione.
- Se `delete_cookie` al logout usa attributi allineati a `Secure`/`SameSite=None` (clear cookie cross-site a volte fallisce se gli attributi non coincidono).

---

## 2. Accessi contemporanei (multi-dispositivo)

### GIÀ PRESENTE
- Ogni login / register / Google / MFA verify chiama `_set_auth_cookies` + `store_refresh` → **nuovo `jti`**, insert aggiuntivo.
- Logout revoca **solo** il `jti` del cookie corrente → le altre sessioni restano.
- Modello di fatto: **sessioni parallele permesse**, senza tetto.

### PARZIALMENTE PRESENTE
- Cleanup scaduti in `store_refresh` (`delete_many` su `expires_at < now`) è opportunistico, non un job dedicato.
- Nessun indice dedicato trovato in `ensure_indexes` su `refresh_tokens` (solo uso runtime).

### ASSENTE
- Limite “N dispositivi”.
- Lista sessioni per utente / “disconnetti tutti gli altri”.
- Binding device/IP/UA sul documento `refresh_tokens` (solo `jti` + `user_id` + tempi).
- UI gestione sessioni.

### DA VERIFICARE
- Quanti `jti` medi per utente in Mongo reale.
- Se un secondo login dallo stesso browser **sovrascrive** il cookie (sì) lasciando l’old `jti` orfano in DB fino a TTL (sì: sessione “fantasma” ancora valida se qualcuno ha ancora quel cookie — tipico solo se cookie era stato copiato).

---

## 3. Logout e revoca

### GIÀ PRESENTE
- Logout: `revoke_refresh(cookie)` + clear access/refresh/csrf.
- Self-erase: stesso pattern + `erase_user_data` cancella `refresh_tokens` per `user_id`.
- Test L12: dopo logout, refresh con stesso cookie → **401** (`test_phase23_refactor.py`).

### PARZIALMENTE PRESENTE
- Revoca = **delete** del record (non `revoked_at` append-only) — coerente con B12 “oggi non c’è audit sessioni”.
- Logout **non** invalida l’access già emesso: resta usabile fino a max ~15 min.
- `change_password` / `reset_password`: **non** revocano refresh (né “tutti i dispositivi”).
- Erase Ops (`bridge_erase_user`) passa da `erase_user_data` → cancella i refresh dell’utente; access residui fino a exp.

### ASSENTE
- `revoke_all_sessions(user_id)` riusabile (password change, suspend, Founder).
- Revoca access immediata.
- Audit strutturato di logout/revoca (B12).

### DA VERIFICARE
- Comportamento cookie clear su domini `cloud.` / `www.` / API cross-site.

---

## 4. Riutilizzo di token già revocati

### GIÀ PRESENTE
- Dopo logout, `is_refresh_valid` fallisce → 401 (`invalid_token`).
- Refresh scaduto: `decode_token` → `None` (ExpiredSignature) → 401 (stesso dettaglio generico).
- Access scaduto/ invalido: `get_current_user` → 401; FE tenta refresh.

### PARZIALMENTE PRESENTE
- Replay del **refresh ancora in store** (non revocato): **sempre permesso** — è il design senza rotazione.
- Replay dell’**access** entro TTL: sempre permesso (stateless).
- `jti` assente sul refresh → `is_refresh_valid` False; `store_refresh` senza `jti` non inserisce nulla (no-op silenzioso).

### ASSENTE
- Rilevamento reuse-after-rotate (impossibile senza rotazione).
- Famiglia di sessioni / kill-tree se un refresh rubato viene riusato dopo rotazione.

### DA VERIFICARE
- Distinguibilità client 401 “scaduto” vs “revocato” (oggi stesso codice messaggio).

---

## 5. Rotazione dei refresh token

### ASSENTE (confermato)
- `POST /auth/refresh` **non** chiama `create_refresh_token`, **non** `store_refresh` nuovo, **non** `revoke` del vecchio.
- Il cookie `refresh_token` resta invariato per tutta la vita della sessione (fino a 7g o logout).

### PARZIALMENTE PRESENTE
- Nuovo refresh solo su **nuovo login** (o register / Google / MFA verify / cloud register), non sul rinnovo silenzioso.

### GIÀ PRESENTE (correlato, non rotazione)
- `jti` univoco a emissione + store server-side = base necessaria per introdurre rotazione in seguito **senza** riscrivere il modello.

### DA VERIFICARE
- Se in roadmap si vuole rotazione a ogni refresh o solo a intervalli / su suspicious reuse.

---

## 6. Percorsi di emissione sessione (inventario)

| Percorso | Store `jti`? | Note |
|---|---|---|
| `POST /auth/register` | Sì (`store_refresh`) | |
| `POST /auth/login` | Sì | Se MFA: cookie **dopo** `/auth/mfa/verify` |
| `POST /auth/mfa/verify` | Sì | |
| `POST /auth/google` | Sì | |
| `POST /cloud/auth/register` | Sì | |
| `POST /invites/accept` | **No** | Setta cookie access+refresh ma **non** chiama `store_refresh` |
| `POST /auth/refresh` | N/A | Non emette nuovo refresh |

### Gap rilevante (solo lettura)
Accept invite: il refresh in cookie **non** è nel store → al primo silent refresh dopo ~15 min la sessione post-invito tende a **401**, a meno di nuovo login. Access immediato funziona. Cookie hardcodati `secure=True, samesite=none` (non passano da `_cookie_kwargs()` / `COOKIE_SECURE`).

---

## 7. Contenuto record / sicurezza cookie

**Store:** `jti`, `user_id`, `expires_at` (claim JWT `exp`), `created_at`. Niente IP, UA, label dispositivo, `last_used_at`.

**Cookie:** HttpOnly (JS non legge i token). CSRF double-submit quando Secure. Bearer `Authorization` ancora accettato da `get_current_user` (path parallelo ai cookie; senza refresh automatico).

**Segreto:** un solo `JWT_SECRET` HS256 per access e refresh.

---

## Rischi tecnici (senza proporre riscrittura)

1. **Nessuna refresh rotation** → furto del refresh cookie = sessione fino a 7 giorni o logout su quel cookie.
2. **Access non revocabile** → finestra post-logout / post-erase fino a 15 min.
3. **Password change/reset non killano le altre sessioni.**
4. **Accept invite senza `store_refresh`** → sessione fragile / refresh morto.
5. **Multi-device illimitato** senza inventario o “logout ovunque”.
6. **Revoca = delete** → nessun audit B7 punto 6 (allineato a B12).

Cose già solide da **mantenere**: cookie HttpOnly, store `jti`, check su refresh, test L12 logout→401, FE single-flight, CSRF con esenzione consapevole del refresh, `is_active` sul refresh.

# B14 — Audit tecnico: protezione login

**Sola lettura.** Nessun file modificato. Nessuna correzione applicata.

## Fotografia dello stato attuale

OMNIA ha **una sola protezione brute-force dedicata al login password**, su `POST /api/auth/login`:

- **5 tentativi falliti** / **15 minuti** di blocco  
- Chiave Mongo: `ip:email` in `login_attempts`  
- File: `backend/shared/auth/brute_force.py` (righe 5–46)  
- Uso: `backend/apps/core/auth.py` `login()` (righe 220–247)

**B2B e B2C password** condividono lo stesso endpoint `/api/auth/login` (stesso form FE `LoginPage.jsx`). Non esiste un login password B2C separato.

**Google** (`POST /api/auth/google`) e **MFA verify** (`POST /api/auth/mfa/verify`) **non** usano `brute_force` né un rate limit auth dedicato.

Il rate limiter generico (`shared/security/rate_limit.py`) protegge registrazione cloud, search, contact, email, feed, ecc. — **non** il login.

Checklist interna (`memory/SECURITY_CHECKLIST.md` A2) marca brute-force come ✅; in realtà è **efficace solo sul percorso password unico IP+email**, con lacune concrete sotto.

---

## 1. Login B2B, B2C e Google

### GIÀ PRESENTE
- **Password unificato** B2B/B2C: `POST /api/auth/login` → `is_locked` → fail → `register_failed_attempt` → success → `clear_attempts` (`auth.py` 227–247).
- Credenziali invalide / utente assente → stesso 401 (`invalid_credentials`) — riduce enumerazione email sul login.
- Account `!oauth:google` → 401 `use_google_sign_in` **senza** incrementare il contatore (riga 237–238).
- Account disabilitato → 403 **dopo** password corretta (244–245); non fa clear degli attempt.
- **Google**: verifica ID token Google (`google_auth.py` `_verify_google_id_token`, 44–72); `is_active` su utente esistente (144–145); MFA gate (165–174).

### PARZIALMENTE PRESENTE
- B2C: registrazione ha rate limit IP (`cloud_auth.py` 56–58, 10/h); login password no percorso dedicato.
- Google dipende da Google (anti-abuso lato IdP), ma **nessun** limite OMNIA su tentativi di token invalidi / churn account.

### ASSENTE
- Brute-force / rate limit su `/auth/google`.
- CAPTCHA / Turnstile / proof-of-work sul login.
- Rate limit su `POST /auth/register` B2B (solo cloud register ce l’ha).

### DA VERIFICARE
- Se in produzione un reverse proxy **sovrascrive** `X-Forwarded-For` (vedi §3): `_client_ip` si fida del primo hop (`auth.py` 115–119).

---

## 2. Tentativi massimi e durata blocco

### GIÀ PRESENTE
| Parametro | Valore | Dove |
|---|---|---|
| `MAX_ATTEMPTS` | **5** (costante hardcoded) | `brute_force.py:5` |
| `LOCKOUT_MINUTES` | **15** (hardcoded) | `brute_force.py:6` |
| HTTP blocco | **429** + `auth.too_many_attempts` | `auth.py:227–228` |
| Indice | `login_attempts.identifier` | `connection.py:180` |

Logica blocco (`is_locked`, 13–28): `count >= 5` **e** `last_attempt` entro 15 minuti.

### PARZIALMENTE PRESENTE
- Dopo lo sblocco temporale il **`count` non viene azzerato**. Un solo nuovo fallimento riporta subito in lockout (count ancora ≥ 5, `last_attempt` aggiornato). Reset solo con login riuscito (`clear_attempts`).
- Nessuna env var: non regolabile in produzione senza deploy codice.

### ASSENTE
- Blocco progressivo (backoff crescente).
- Blocco permanente / escalate dopo N finestre.
- Notifica utente/admin su lockout.

### DA VERIFICARE
- Comportamento clock skew / ISO timestamp mixed string vs datetime in Mongo (il codice gestisce entrambi in `is_locked`).

---

## 3. Aggiramento cambiando IP, email o identificativo

### GIÀ PRESENTE
- Identificativo composito `f"{ip}:{email}"` (`brute_force.py:9–10`) — corretto per non fondere tutti gli utenti dello stesso NAT in un solo lock, ma…

### PARZIALMENTE PRESENTE / rischio concreto
| Aggiramento | Effetto |
|---|---|
| **Cambio IP**, stessa email | Nuovo `identifier` → contatore a zero. Bot multi-IP / proxy = **bypass del tetto 5**. |
| **Cambio email**, stesso IP | Nuovo identifier → spray password su molte email dallo stesso IP **senza** lock IP globale. |
| **Spoof `X-Forwarded-For`** | Se il edge non riscrive l’header, l’attaccante sceglie l’IP nel lockout (`_client_ip` 115–119; stesso pattern in `rate_limit.client_ip`). |
| Password errata vs utente inesistente | Entrambi incrementano — ok anti-enum sul fail path. |

### ASSENTE
- Contatore **per account** (email) indipendente dall’IP.
- Contatore **per IP** trasversale a tutte le email.
- Trust proxy esplicito / uso di IP connessione reale quando XFF non è fidato.

### DA VERIFICARE
- Config Railway/proxy: chi imposta `X-Forwarded-For` in produzione.

---

## 4. Rate limiting IP / account / altri

### GIÀ PRESENTE (fuori login, utile come contesto)
`enforce_rate_limit` / `enforce_ip_rate_limit` (`rate_limit.py`): rolling window Mongo `rate_limit_events`.

Usato su: `cloud_register` (10/h), search/map/contact, scout, planimetria/visura, feed/publishing, email to/global (`email/client.py` 166–178).

### ASSENTE sul login
- Nessun `enforce_ip_rate_limit` su `/auth/login`, `/auth/google`, `/auth/mfa/verify`, `/auth/forgot-password`, `/auth/register` B2B, `/auth/refresh`.
- Nessun rate limit **per account** dedicato oltre al composito ip+email di `login_attempts`.

### PARZIALMENTE PRESENTE
- Email reset: rate limit solo se parte l’invio (`email_to` 30/h) — `forgot_password` non ha gate prima; risposta sempre 200 (`auth.py` 497–530).

### DA VERIFICARE
- Crescita illimitata di `rate_limit_events` / `login_attempts` (no TTL su `login_attempts`; rate_limit senza expire index nel bootstrap visto).

## 5. Attacchi distribuiti e automatizzati

### GIÀ PRESENTE
- bcrypt su verify (costo CPU per tentativo).
- Cookie HttpOnly + CSRF su mutazioni (login stesso esente CSRF, coerente).
- Script soft-check preprod/stress che sparano 6 login bait e si aspettano 429/401 (`preprod_confidence_gate.py` 306–340).

### ASSENTE
- CAPTCHA / bot detection.
- Device fingerprint / anomaly.
- WAF / edge rate limit documentato nel repo.
- Protezione credential stuffing distribuita (manca lock per-email).
- Slowdown artificiale o coda dopo N fail.

### PARZIALMENTE PRESENTE
- MFA opzionale riduce account takeover se abilitato; non è obbligatorio e la verify MFA non è rate-limited.

### DA VERIFICARE
- Rate limit a livello infrastruttura (Railway, Cloudflare) non visibile dal solo codice.

## 6. Gestione tentativi falliti e registrazione eventi

### GIÀ PRESENTE
- Upsert `login_attempts`: `identifier`, `count`, `last_attempt` (`register_failed_attempt` 31–41).
- Clear su login password riuscito (anche prima del MFA challenge — riga 247 poi 249–256).

### PARZIALMENTE PRESENTE
- Non è un audit append-only (B12): è un **contatore mutabile**.
- Nessun evento “login_failed” / “lockout_triggered” consultabile.
- Login **riuscito** non scrive nulla in `login_attempts` (solo delete).

### ASSENTE
- Storico tentativi (IP, UA, esito) per Admin/Super Admin.
- Alert Ops su spike di 401/429 login.
- Registrazione fail su Google token invalid / MFA invalid.

Allineato a B12: punto B7 “login riusciti/falliti” resta scoperto come audit.

## 7. MFA e account temporaneamente bloccati

### GIÀ PRESENTE
- Dopo password (o Google) OK con MFA: challenge JWT 5 min (`MFA_CHALLENGE_MINUTES = 5`, `mfa_routes.py:32,53–60`); cookie sessione solo dopo `/mfa/verify`.
- `mfa_verify` controlla `is_active` (186–187).
- Backup codes consumati su uso.

### PARZIALMENTE PRESENTE
- `clear_attempts` avviene **alla password corretta**, prima della MFA → chi conosce la password esce dal lockout password e può provare TOTP liberamente.
- Lockout password: blocco **per quella coppia ip+email**, non “account suspended” globale.

### ASSENTE
- Rate limit / lockout su `/auth/mfa/verify` (brute TOTP ~10⁶/30s teorico; in pratica limitato da rete ma senza tetto app).
- Integrazione lockout password ↔ challenge MFA.
- UI che distingua “account bloccato 15 min” con countdown (FE mostra solo `formatApiErrorDetail` del 429).

### DA VERIFICARE
- Quanti utenti produzione hanno `mfa_enabled`.

## Vulnerabilità e rischi concreti

1. **Bypass lockout via IP rotation** (identifier `ip:email`) — credential stuffing distribuito.
2. **Nessun tetto per-IP** su molte email — spray dallo stesso host.
3. **X-Forwarded-For spoofabile** se il proxy non sanitizza — bypass triviale del lockout.
4. **MFA verify senza rate limit** dopo password nota; clear lockout pre-MFA.
5. **Google / forgot-password / register B2B** senza anti-brute dedicato (reset = enumerazione soft + carico email mitigato solo a invio).
6. **Count non reset post-finestra** → un fail ri-blocca; UX dura, non sicurezza extra contro multi-IP.
7. **Test CI deboli** sul 429 reale.
8. **Nessun audit consultabile** dei fail (B12).

Severità: non è “login aperto”; è **protezione single-node** insufficiente contro attacchi distribuiti e contro la seconda fase MFA.

- Messaggi fail uniformi password/utente.
- bcrypt + clear su successo.
- Indice `identifier`.
- Gate MFA post-password/Google (challenge 5 min, no cookie prima).
- Rate limit su **register cloud** e su email outbound.
- Separazione account Google-only (`use_google_sign_in`).
- Soft-check bait email (non lockare il Founder).

Non riscrivere l’auth: **estendere** questo pezzo.

## 2. Registrazione B2B e B2C

### GIÀ PRESENTE

**Switch agenzia:** `backend/apps/core/auth.py` — `my_agencies()`, `set_active_agency()` (solo id ∈ `agency_ids`).

**Login bootstrap:** `login()` imposta `active_agency_id` se una sola membership e active assente/invalida.

**Gap:** JWT access include `role` in payload (`jwt_tokens.create_access_token()`), ma **`get_current_user` usa il ruolo dal DB** (corretto). Il middleware usa prima `payload.role` poi sovrascrive col DB solo per agency, non sempre allineato al ruolo DB nel primo tick (minore).

---

## 6. Holding / group / branch

**Modelli:** `backend/shared/models/agency.py` — `AgencyGroupInDB`, `AgencyInDB.group_id`, `branch_code`.

**API:** `backend/apps/immoweb/groups.py`
- `create_group()` — promote a `group_admin` (super_admin mantiene ruolo, setta `group_id`).
- `_load_accessible_group()` / `_require_group_write_access()` — read vs write group.
- `list_branches()`, `group_consolidated_kpis()` — KPI cross-branch per chi ha accesso al group.
- `attach_branch()` — anti hijack: non-`super_admin` solo agenzie owned o già in `agency_ids`.

**Admin org A vede org B?**
- **CRM tenant (clients/properties/…):** di norma **no** — scope = `active_agency_id` (+ tenant inject). `group_admin` vede rollup su route `/groups/{id}/consolidated` e lista API keys multi-branch (`api_keys.list_api_keys()`), **non** un merge automatico su tutte le collection CRM senza cambiare active agency.
- **`super_admin`:** bypass tenant inject + cabina + **impersonation** (`founder_bridge.bridge_impersonate()` muta `agency_ids` / `active_agency_id`).

**Gap documentazione vs codice:** header `groups.py` dice che `group_admin` «read/write across all branches»; implementazione CRM resta **per-tenant attivo**, salvo endpoint group espliciti.

**Gap access check:** `_load_accessible_group()` contiene condizione `if group_id in {ag for ag in (user.get("agency_ids") or [])}` — confronta **group_id con agency_ids** (probabile bug logico nell’audit).

## 8. Assegnazione ruoli

| Percorso | Funzione | Regole |
|----------|----------|--------|
| Registrazione | `auth.register()` | Solo `client`/`student` |
| Crea agenzia | `agencies.create_agency()` | Promote owner → `agency_admin` (non se già `super_admin`) |
| Invito | `invites.create_invite()` / `accept_invite()` | Ruolo invite: `agent` \| `agency_admin`; accettazione: nuovo user = ruolo invite; esistente: ruolo aggiornato **solo se** era `client` |
| Crea group | `groups.create_group()` | → `group_admin` (+ `group_id`) |
| KYC auto-attiva | `kyc_auto_activate` (blocco owner) | Promote owner a `agency_admin` se ruolo non già privilegiato |
| Seed | `seed_admin()` | `super_admin` da env |

**Assente:**
- **PATCH ruolo membro** (nessun endpoint trovato).
- **Vincolo delega** («inviti solo ruoli ≤ del mio»): `create_invite()` non limita `agency_admin` a invitare solo `agent`.
- **Audit trail dedicato ai cambi ruolo** (solo log applicativi generici / `consent_log` per register/erase).

**Rimozione da agenzia:** `agencies.remove_member()` — `$pull` `agency_ids`, non delete user, non cambia `role`.

## 10. `is_active` / sospensione vs unlink

| Entità | Comportamento |
|--------|----------------|
| **User `is_active`** | Controllato in `login()`, `refresh()`, `google_auth` — **non** in `get_current_user()`. Disabilitazione: `erase_user_data()` → `is_active: False` (`shared/privacy/erasure.py`). Nessun endpoint «suspend member» trovato. |
| **Unlink agenzia** | `remove_member()` — membership only |
| **Agency `is_active` / `activation_status`** | `pending` \| `active` \| `suspended`; CRM gate: `assert_agency_crm_unlocked()` |
| **API key `is_active`** | Revoca separata da user |

## 11. `get_current_user` senza check ruolo/agenzia

**Comportamento intenzionale di `get_current_user()`** (`dependencies.py`):
- Autentica JWT + user esistente.
- Non verifica ruolo privilegiato né `is_active`.
- Opzionale: imposta tenant context da `active_agency_id` se valida.

Endpoint che si affidano solo ad esso + **helper tenant interni** (es. `require_agency_membership` in AL) **senza** `require_roles` sono accessibili a **qualsiasi** utente autenticato con membership valida (inclusi `client`/`student` se avessero `agency_ids` anomali).

## Riepilogo gap (fatti, non redesign)

1. **Nessun RBAC granulare** — solo `role` + tenant + pochi gate (`activation_status`, B2C, privacy L1–L4).
2. **`branch_*` ruoli** nel tipo ma **quasi mai assegnati**; franchising si appoggia agli alias di `agency_admin`/`agent`.
3. **`group_admin` cross-branch CRM** limitato rispetto al commento modulo groups (serve switch `active_agency_id` o route group).
4. **Inviti** non possono invitare `group_admin`/`branch_*`; **nessun PATCH ruolo** membro.
5. **Nessun audit strutturato** dei cambi `role`.
6. **`get_current_user` + access token** non blocca `is_active:false` (sessione fino a scadenza JWT).
7. **`list_members`** senza `require_roles` — agenti leggono elenco membri.
8. **`al_agent`** — qualsiasi utente con membership agenzia può usare tool CRM-scoped (se non bloccato altrove dal FE).
9. **`moderation.py` header** vs `ALLOWED_ROLES` — solo `super_admin`.
10. **`founder` string** in staging — non è `UserRole`.
11. **`_load_accessible_group`** — possibile confronto errato `group_id` ∈ `agency_ids`.
12. **Ruolo nel JWT** non usato per authz BE (DB sì), ma presente nel token.
